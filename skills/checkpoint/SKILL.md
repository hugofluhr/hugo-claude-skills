# Checkpoint

The failure mode this exists to prevent: a session computes a number or derives a
claim in scratch code, states it as a conclusion, and moves on. The conclusion
survives in prose somewhere; the code that produced it does not. Weeks later
nobody — including the agent that wrote it — can tell you how the number was
computed, only what it was.

A checkpoint is not a summary. A summary can be regenerated by re-reading the
conversation. What can't be regenerated is throwaway code — so that's the part
this skill exists to rescue, every time.

This skill is repo-agnostic by design — it should work the same way whether
you're in a neuroimaging repo, a modeling repo, or anything else. Repo-specific
policy (whether to self-trigger, where notebooks live, editing conventions)
belongs in that repo's own `CLAUDE.md`, not here.

## Procedure

**1. Find every claim made this session that isn't backed by rerunnable code.**

Scan back through the conversation (since the last checkpoint, or the start of
the session) for numbers, statistics, or decisions stated as settled — not
intermediate sanity checks, the ones that would show up in a findings summary or
get repeated in a future conversation. For each one, ask: does the exact code
that produced it already live in a notebook cell or script in this repo?

- **Yes** → note which cell/script, move on.
- **No** → fold it in now, before writing the session note. Prefer adding it to
  the notebook or script it's most relevant to, as a new, clearly dated
  cell/section — don't silently overwrite an existing conclusion it contradicts;
  flag the contradiction next to it instead and leave adjudication open unless
  it was actually resolved this session. If it isn't tied to any existing
  notebook and doesn't warrant a new one, put the fenced, rerunnable code block
  directly in the session note itself. A prose description of what was computed
  ("grouped by X and took the variance") does not count — it must be code that
  can be pasted and rerun.
- Check this repo's `CLAUDE.md` for notebook-editing conventions before
  touching any `.ipynb` (e.g. some repos require `NotebookEdit` over `Write`).

**2. Write or update the session note.**

Path: `session-notes/YYYY-MM-DD_topic-slug.md` in the current repo, using
today's date and a short kebab-case slug for the session's main thread. Create
the `session-notes/` directory if this is the first checkpoint in this repo. If
a note for the same date *and* topic already exists (a second checkpoint later
in the same session, or picking the same thread back up), update it in place —
don't create a numbered duplicate. A different topic on the same day is a new
file; multiple sessions per day on different threads is expected and fine.

If this repo already has earlier session notes, read one before writing to
match its established *structure* — section names and ordering. Do not match
their length if they're long; keep new entries tight regardless of precedent.
Otherwise, use this default shape:

- Title + date, and a link to a companion note if this extends earlier work.
- One line on how the session started vs. where it actually went, if it detoured.
- **Findings** — numbered. Each one: the actual number/claim, a pointer to
  where the derivation now lives (which notebook, which cell/section, which
  script), and the one-line consequence. Aim for 2–4 lines per finding, not a
  paragraph. The session note is an index you search and skim, not a report
  you read end to end — the full reasoning belongs in the notebook's markdown
  cells, next to the code that backs it, not duplicated here. If a finding
  genuinely needs more than that to state correctly, that's a sign it belongs
  in the notebook and the session note should just point at it.
- **Code shipped** — table of what changed, and its git state (merged/branch/uncommitted).
- **Data produced**, if anything ran on a cluster/VM — what, where, and any
  verification performed.
- **Git state at session end** — branch, whether local/remote agree.
- **Open threads** — numbered, concrete, one line each, each one actionable by
  a future session without needing this conversation's context to interpret it.

**3. Stage, don't commit.**

`git add` the session note and every notebook/script touched in step 1. Do not
run `git commit` — that happens only when the user asks. Report exactly what
got staged and propose a commit message (one line, imperative, mentioning the
session-note filename so `git log --grep` can find it later).

**4. Report back concisely.**

What was rescued into code (and where), what's now in the session note, what's
staged. Skip re-explaining findings the user was already present for.
